# 协作流程细节

`$ROOM` 代表 `python3 <skill 目录>/scripts/room.py`，`AGENT_ROOM` 已指向当前聊天室。示例里主持人是 claude、对方是 codex；反过来把两个名字对调即可。

## 评审（最常用）

1. 把要评审的内容落到文件里：计划、结果表、改动的代码。消息里只写问题和关注点。
2. 调用对方：

   ```sh
   $ROOM ask --as claude --peer codex --mode review --ref eval_plan.md --ref probe.py \
     "请复核 eval_plan.md。重点：选参是否按 donor 隔离；置信区间的算法；有没有在测试集上做了选择。"
   ```

3. 逐条处理对方的意见。每一条先自己核实它引用的证据，再归入三类：采纳、不采纳（写明依据）、无法判断（缺什么信息）。
4. 把处理结果整合成一条 proposal（结论、采纳了什么、没采纳什么及依据），用 `--mode propose` 交给对方表态，然后按下面“走到一致，或者列明分歧”继续。评审本身不等于对方同意你的结论。
5. 向用户汇报时保留对方的原始意见编号，方便对照。

对方被要求区分“有问题”和“我没法核实”，并且没有问题时直说。如果它的回复里全是泛泛的建议而没有路径、行号或数字，把它当成未核实的意见。

## 独立作答后比较

用于需要两份互不影响的判断时，例如方案选择或结果解读。

1. 先自己完成答案，写进一个文件。**写完之前不要调用对方。**
2. 调用：

   ```sh
   $ROOM ask --as claude --peer codex --mode independent --seal my_answer.md \
     "任务：……（把完整的任务说明写在这里，对方只能看到这一条）"
   ```

3. 脚本依次做四件事：
   - 计算 `my_answer.md` 的 SHA-256，记进任务消息。这相当于先交卷。
   - 用全新的会话调用对方，只给它这条任务消息，不给聊天室里的其他内容。
   - 把对方的回复记为 `draft`。
   - 再把你的文件内容记为 `draft`，并核对哈希。如果文件在对方作答期间被改过，会追加一条说明，这一轮的独立性不能算数。
4. 两份草稿都在聊天室里了。比较时分别列出：双方一致的部分、各自独有且经核实成立的部分、互相冲突的部分。不要为了折中把互不相容的方案拼在一起。
5. 用 `propose` 把整合后的结论交给对方表态。

向用户展示时同时给出两份原始草稿的编号和最终结论，不要只给整合后的版本。

## 讨论并形成结论

```sh
$ROOM ask --as claude --peer codex --mode propose \
  "结论：……
理由：……
成立的条件：……
还不确定的：……"
```

一条好的 proposal 自己就能读懂：结论、理由、成立的条件、还不确定的地方。它的内容哈希会被记录，对方的表态绑定这个哈希。

proposal 的状态用 `$ROOM status` 查看：

| 状态 | 含义 |
| --- | --- |
| 待表态 | 另一方还没有对这个版本明确同意或不同意 |
| 已达成一致 | 另一方对这个版本明确同意 |
| 有分歧 | 另一方明确不同意 |
| 已被新版本取代 | 提出方发了一条 `--reply-to` 指向它的新 proposal |

对方不同意时，按它列出的条目修改，然后：

```sh
$ROOM ask --as claude --peer codex --mode propose --reply-to 12 "修订后的结论：……"
```

用户提出的 proposal 需要两个 agent 都同意才算一致。

### 走到一致，或者列明分歧

一场讨论只有两种合格的结局，由 `$ROOM outcome` 判定：

| `outcome` 的输出 | 退出码 | 含义 | 对用户怎么说 |
| --- | --- | --- | --- |
| 已达成一致 | 0 | 所有没被取代的 proposal 都得到了对方的明确同意 | “已达成一致”，给出 proposal 和同意消息的编号 |
| 未达成一致 | 1 | 还有 proposal 被不同意或没表态；输出里附对方不同意的原文 | “未达成一致”，逐条列出分歧 |
| 没有可表态的结论 | 3 | 聊天室里没有 proposal | “对方没有对结论表态” |

对方不同意时，逐条处理它的意见：

1. 自己核对每一条引用的证据。
2. 全部接受：改好，用 `--reply-to` 发新版本，等对方 `agree`。这一步不能省，你改完不等于对方同意。对方被要求一次把意见提完，所以只按它的条目修改的版本通常下一轮就会通过。
3. 部分不接受：在新版本里写明哪条没采纳、依据是什么，再发。
4. 同一个分歧点双方各说过两次、谁也没有新证据，就停止在这一点上往返。能拆开的话，把双方都同意的部分单独发一条 proposal 取得同意；没谈拢的点留在分歧清单里。
5. 同一个结论最多 6 个版本，脚本会拒绝第 7 版。到了上限按谈不拢处理。

分歧清单每条四项：分歧点；你的立场和依据；对方的立场和依据（引用消息编号，用原话）；缺什么信息或谁来决定。不要为了让状态变成“已达成一致”而接受一条你核实后认为不对的意见，也不要删掉分歧点来换取同意。

主持人自己记一条 `decision`、或者口头说“我已经按它的意见改了”，都不改变 `outcome` 的结果。

## 分工写代码

对方默认只读。确实需要它改文件时：

- 先取得用户同意，再用 `--write --cd <它负责的目录>`。
- 在消息里写清：改哪些文件、不能碰哪些、做完用什么命令验证。
- 同一个文件同一时间只有一方在改。需要两边同时写时，各用各的目录或 git worktree。
- 对方改完后自己看实际的 diff 并运行验证，不只看它的总结。
- 不让对方提交、推送、合并或部署，除非用户明确要求。

## 双开模式

用户同时开着两个交互式会话时，两边都按下面做：

```sh
$ROOM read --as codex                 # 读别人发的未读消息，并前移自己的游标
$ROOM post --as codex --kind review --reply-to 7 "……"
$ROOM post --as codex --kind agree --reply-to 9 "同意这一版。"
$ROOM wait --as codex --timeout 300   # 最多等 5 分钟，等到就打印并退出
```

没有任何机制会唤醒对方。发完消息告诉用户需要对方查看，由用户去另一个会话说一声；或者自己等一次 `wait`。`wait` 单次最长 30 分钟，不要写循环。

用户可以在终端里实时看聊天室，也可以自己发言或直接提问：

```sh
$ROOM tail                            # 持续显示新消息，Ctrl-C 退出
$ROOM post --as user "补充：只比较 3M 的两个模型。"
$ROOM ask --as user --peer codex "你怎么看 #12？"
```

## 消息类型

| 类型 | 谁用 | 说明 |
| --- | --- | --- |
| `msg` | 任何人 | 普通消息 |
| `task` | 发起方 | 独立作答的任务说明 |
| `draft` | 双方 | 独立作答的草稿 |
| `review` | 评审方 | 评审意见 |
| `proposal` | 任何人 | 需要表态的具体结论 |
| `agree` / `disagree` | 另一方 | 必须 `--reply-to` 一条别人的 proposal |
| `decision` | 主持人 | 可选：向用户报告前，把最终结论单独记一条 |
| `note` | 任何人、脚本 | 备注；脚本用它记录调用失败等情况 |

单条消息上限 20 万字符。更长的内容写进文件，用 `--ref` 引用路径。

## 对方能看到什么

- **新会话**：最近 30 条消息（`--context N` 可调），总长超过 6 万字符时从最旧的开始省略，并告诉对方省略了几条以及聊天室目录在哪，它可以自己去读。
- **续接会话**：只发它上次发言之后的新消息。续接失败（例如会话已过期）时自动改用新会话重试一次，并带上完整记录。
- **独立作答**：只有任务消息这一条。
- 每次都带上：它的身份、只读还是可写、用户定的规则、这次的模式说明。

每次调用的完整提示词、命令、耗时和退出码都留在 `<聊天室>/calls/` 里，用户可以直接查看。

## 用户追问时

| 用户说 | 做法 | 调用对方 |
| --- | --- | --- |
| 结果在哪、给我看看 | 给出已有结论和消息编号，或 `$ROOM log` | 否 |
| 现在到哪了 | `$ROOM status` | 否 |
| 你们一致了吗 | `$ROOM outcome`；未一致时把分歧原样告诉用户 | 否 |
| 为什么这样定 | 用聊天室里已有的理由回答 | 否 |
| 条件变了、再考虑某一点 | 针对原结论再问一次 | 是，一次 |
| 重新讨论 | 新开一个聊天室，旧的保留 | 是 |

## 什么时候停

- `$ROOM outcome` 显示已达成一致。
- 谈不拢：同一个分歧点双方各说过两次仍无新证据，或同一个结论到了第 6 版。带着分歧清单向用户汇报，第一句说“未达成一致”。
- 对方调用失败：不重试超过一次，告诉用户失败原因（见 `calls/` 里的记录）。登录过期、额度用完这类问题需要用户处理，不要换账户或换模型绕过去。
- 用户的规则不允许继续，或者继续下去需要 `--write`、`--unsandboxed` 而用户还没同意。
