# 通用科研协作

**模型设计原则（Less is more）。** 每轮从足以回答研究问题的最简基线出发。三方规划时指出基线的具体不足；Claude 派工时只选验证当前假设所需的改动，Codex 按单实现。提出额外模块、损失项、超参数或训练技巧时，说清它解决什么问题，以及怎样用简单对照检验贡献。验收时，若收益落在评估波动范围内或现有证据无法区分两种方案，保留简单版本为默认，把复杂方案记作待验证假设。

## 第零步：从空白会话确认调用来源

**启动问询主会话**默认使用用户自己的 Claude Code、Opus 5.5、Extra High（`xhigh`），负责询问研究目标、数据位置、授权范围和各角色配置。用户可显式另选启动配置。新开该主会话时可运行：

```sh
claude --model claude-opus-5-5 --effort xhigh
```

在该会话输入 `/research-agent`。已经打开的会话沿用客户端实际设置；Skill 文字本身无法切换已经处理当前消息的模型。启动时分别确认并记录常驻主控、深度判断会话以及 Gemini 和 Codex 的客户端、型号与推理强度。用户对本项目的明确选择优先。

首次启动先在当前聊天向用户展示并询问「每个角色使用哪个客户端、哪个型号；这组来源和型号可以吗？」等用户明确选择后再派工。模型和客户端分别记录。不要把上次会话的选择、已安装客户端或同名模型当成本次来源授权。若用户已在本次请求明确给出整组，复述后采用；只补问未指定的项。选定的路由沿用到本项目的返工和后续轮次。

| 角色 | 建议的独立来源 | 型号示例 |
|---|---|---|
| Claude 常驻主控、常规审核 | 用户自己的 Claude Code 登录 | Opus 5.5 |
| Claude 独立规划、关键科研审核、争议裁决建议 | 同一 Claude Code 账户，另开会话 | Fable 5.2，Extra High |
| Gemini 独立规划和独立验收 | Antigravity 的 Google 登录 | Gemini 4 Neon High（`--gemini-model gemini-4-neon-high`） |
| 独立规划、执行、修改、自检与结果解读 | 当前 Codex 会话；单轮脚本启动目标机器上的 Codex CLI | 当前配置，或明确指定 `--codex-model` |

只有用户明确选择让 Antigravity 提供 Claude 时才用 `--claude-agy-model`。某一入口认证失败、型号不可用或额度耗尽时，保留已完成阶段，告知哪个来源失败；换客户端或账号须由用户另选。路由记录表示请求的客户端与型号；服务返回的实际型号或登录方式可另记，实际扣费以各账户账单为准。

### Claude 在各阶段的分工

常驻 Opus 负责收件、汇总派工、检查作业状态和维护项目进度页。第三步常规代码检查由 Opus 对照派工单放行；需要判断方法或评估设计能否回答研究问题时，调用已确认的 Fable 配置提出意见。
第一步由独立的 Fable 会话提交 Claude 的规划稿。第四步若要解释关键结果、区分竞争假设或判断研究方向，由新的 Fable 会话完成 Claude 的独立验收；例行按表核对可用独立 Opus 会话。两者都遵守相同的证据隔离规则。
第五步意见一致且达标时由 Opus 收尾。三份报告封存后，若分歧足以改变结论，或下一步将投入大量计算资源，Opus 把原始证据、争议点和备选方案交给新的 Fable 会话，请其给出裁决建议。最终由 Opus 记录采纳理由并派工。主控日志登记每次深度调用的阶段、型号和触发原因。
分阶段选型由五步流程的主持会话执行。单轮辅助脚本的 Claude 型号参数适用于该次脚本的全部 Claude 调用。

### 冷启动验收

在新终端或全新主持会话中，清空本次任务的选择，保留用户原有登录。从仓库根目录运行以下预览；它只询问并打印路由，不读研究数据、不连 SSH、不发模型请求。

```sh
python3 skills/research-agent/scripts/research.py --show-routing
```

1. 验证先看见 Claude 来源选项，以及 Gemini 和 Codex 各自的固定入口；再填写各角色型号。对话主持者应在聊天中提问，不能为用户抢先填 `--use-defaults`。
2. 选择 Claude Code 后检查预览为 `claude / agy / codex`。改选 Antigravity 的 Claude，再次检查主控为 `agy`。非交互运行须传各角色选择；用户明确接受其余默认值时可加 `--use-defaults`。
3. 用模拟 CLI 检查实际执行参数和失败路径。Claude Code 失败应停在该阶段，其他订阅不接管。把预览、模拟调用和真实服务回报分开记录。预览通过后，正式调用继续使用已确认的同一组参数。

把研究问题、可共享材料、已有证据、预期交付物和验收标准写入任务说明。按研究类型选择证据：文献综述可提供纳入标准和原文，理论研究可提供定义、假设和推导，计算研究可提供数据、代码和运行配置。实验项目可整理设计与观测记录；需要人员或仪器实际完成的步骤应标记待执行。每轮规划时，三位规划者接收相同材料。

首轮选模型时，Claude 一并询问是否有本次任务的限制；用户已说明的直接沿用。计算任务可以问最多同时用几张卡、累计多少 GPU 小时；任何项目都可以设截止时间、费用或轮数。只询问与任务有关的项目。都可以留空，明确说不设或跳过后直接按研究目标推进，不填默认数字，也无需再问。并行卡数、累计用量和轮数分别记录。未设置数值上限不扩大原任务范围或付费授权。

## Claude 主持的五步循环

一次任务沿用用户选定的三方模型。启动时明确研究目标、完成标准、允许的工作范围及用户选填的限制；把任务模式和这些约束带入后续各轮。调用本 skill 的 Claude 会话负责主持循环。现有 research.py 提供串行单轮辅助流程，没有并发规划、执行检查点或五步归档，运行到报告即退出，脚本本身尚未实现下述双审和跨轮恢复。采用五步循环时由主持会话分别调度各阶段，复用脚本中的 CLI 和 SSH 调用方式；调用整个脚本会提前汇总，也可能重复执行任务。

1. **独立规划。** 同时启动 Claude、Gemini 和 Codex，各自在新会话里看同一份原始任务、约束及上一轮已核实的证据。三者分别说明已有结果支持什么、下一步做什么、如何判断达标。三份规划首稿封存后，由主控读取并派工。
2. **Claude 汇总派工。** 主控读取三份规划原稿，说明采纳的方案、分歧和取舍，写明本轮任务、方法、输入、已设限制、应交付的文件及验收标准，并注明检查点、试跑范围、放行所需的证据，再交给 Codex。
3. **Codex 执行并交付原始结果。** 分两次派工。第一次只实现并做小规模试跑，交代码改动、配置和试跑输出后停下。Claude 主控审代码（可用 Claude Code 的 /code-review），再对照派工单核对输出；无代码任务检查关键推导、原文或抽样结果。主控记录通过、返工或证据不足及依据。通过才发第二份指令，让 Codex 正式运行。返工时列出偏差与复验条件，缺证时指出缺少的材料，两者均递增尝试号，重新核对后才能继续。记录实际方法、输入、产物位置与版本；涉及计算或调度时记录配置、命令与作业号。对排队或运行中的作业，主持会话用同一作业号查询进度，完成后读取产物。等待期间停留在第三步。正式产物就绪即冻结验收标准、实际输出、配置和来源索引；不等待 Codex 自检。
4. **三方并行核验。** 同时将同一版只读证据交给三个新会话。Codex 作执行者自检并写自己的结果解读；Claude 和 Gemini 各自独立分析，按验收标准给出证据、复算结果、局限和建议。缺少可访问的远程原件或可核对副本时，标记未核实。
   三个会话只接收冻结证据，不继承派工会话，不接收任何一方的自检、判断或草稿。只开放证据包；临时工作目录本身不保证隔离。主控在参与者无权读取的位置保存首稿。单方失败保留其他首稿，只用同一证据重试失败方。证据变化则对新版本重新发起三方核验。
5. **Claude 总验收并决定转向。** 三份首稿都封存后，主控一并读取 Claude、Gemini 的验收意见和 Codex 的执行者意见，记录三方的共识、分歧，以及采纳或暂缓各项建议的证据理由，对照原目标决定下一步。目标达到则交付。实现错误或产物缺失则列出具体问题，回第三步修正并再次三方核验。实验有效但研究问题尚未回答，且下一轮仍在授权和预算内，则带着本轮证据回第一步。出现超预算、目标变更或必须由用户决定的取舍时暂停，说明需要决定什么。三方有分歧时按证据裁决，保留无法消除的不确定性。

第五步也是可选的人工检查点。展示本轮结论、拟采取的动作，以及已设限额的剩余额度，在派发下一项工作前检查当前会话已收到的用户指示。有新指示就记录并按其调整；已要求暂停时停在检查点。没有新指示时，按原先授权和预算推进，无需逐轮等候确认。以后才到达的指示在收到后处理，并说明已有作业处于什么状态。

首轮明确怎样算完成。每次派工或返工前核对研究目标及用户实际设定的限制。达标则收尾；到达已设上限仍未达标，报告缺口。未设数值上限时，以任务完成、缺少新证据、具体阻碍或需要用户决定的范围变化为停止依据。

## Claude 维护的 Pipeline 进度页（含 token 统计）

启动或恢复项目时，主控先初始化进度页，把页面路径告诉用户。页面写在 `项目/进度/index.html`，用户直接用浏览器打开即可。页面每 5 秒重新加载 `status.js`，用的是重新插入 `<script>` 标签的办法，因为 `file://` 下不能用 fetch。内容包括：

- 按实际轮次展示五步流程；有轮数上限时显示到上限；
- agent 关系图：主控、Claude、Gemini、Codex、集群，正在调用的节点会发光、连线会流动；
- 每个 agent 的累计 token（分输入、缓存读、缓存写、输出四段）和逐次调用表；
- 集群作业和事件时间线。

**启动时初始化**（从 Skill 目录运行，可重复执行）：

```sh
python3 scripts/progress.py 项目目录 init --title 项目名 --limits "≤8 GPU · 最多 2 轮" --max-rounds 2 \
  --cluster JUPITER --model lead="Opus 5.5 · xhigh" --model claude="Fable 5.2 · xhigh" \
  --model gemini="4 Neon · XHigh" --model codex="gpt-6.2-astra · max" \
  --lead-transcript ~/.claude/projects/<目录键>/<会话ID>.jsonl
```

- 会话 ID 可以从会话的 scratchpad 路径中读出。只显式绑定当前项目的主控会话文件。换会话时重新 init 并追加绑定；脚本仅累计工作目录属于项目的消息，按会话与消息 ID 去重。旧版自动选择的路径需重新确认并绑定。未绑定时可从明确登记的调用统计用量。
- 主控用量每次写入时从这个会话记录重新统计，并按 message id 去重，因为同一次响应会写成多行。
- 改了模板后，用 `init --refresh-template` 覆盖 index.html。

**每次交接都当场记录**（参数含义见脚本头部注释）：

- `stage 轮 步 [说明]`：更新当前所处的轮次和步骤。
- `agent 角色 running|waiting|done|failed|idle "任务"`：在调用前后各记一次，节点据此高亮。
- `call 角色 阶段 --model … --from-claude-json|--from-codex-log|--from-agy-json 文件`：在调用结束时记录。也可以直接传 `--input/--output/--total`。拿不到用量时页面标“未记录”。
- `job 作业号 名称 状态 --gpus N`：提交作业和状态变化时记录。
- `event "文字"`：其他重要事件。

**为了拿到 token 数，调用时要选对输出格式**：

| CLI | 怎样取得用量 |
|---|---|
| claude | 用 `claude -p --output-format json`，结果里有 `usage` 和 `duration_ms` |
| agy | 用 `agy -p --output-format json`。答复正文在 `response` 字段，用量在 `usage` 字段（含 `input_tokens`、`output_tokens`、`thinking_tokens`、`cache_read_tokens`、`total_tokens`），另有 `duration_seconds` |
| codex | `codex exec` 在 stderr 末尾打印 `tokens used` 和合计数，只有合计 |

纯文本输出里没有用量，所以每次调用都按上表的格式发。用 json 调用时，要从 json 里取出答复正文，再存成规划稿或验收稿。

如果已经用纯文本调用过 Gemini，可以事后补录：agy 把每次对话都存在 `~/.gemini/antigravity-cli/brain/<对话ID>/.system_generated/logs/transcript_full.jsonl`，每一步都带 token 字段。按时间和首条请求找到对应的对话，然后运行 `call gemini 阶段 --replace N --from-agy-transcript <该目录>`，覆盖第 N 条“未记录”的调用（N 从 1 开始，按 status.json 里的顺序）。累加结果和 json 输出的数一致，已实测核对过。首稿封存前，页面只显示状态，不显示首稿内容。

## 实践经验与排错

- **核实配置要真调用一次。** 每个角色各发一条 "Reply OK"：
  - Claude：看 json 输出里的 `modelUsage`，确认服务端实际用的型号。
  - Codex：看会话头里的 `model:` 和 `reasoning effort:`。
  - Gemini：先用 `agy models` 确认型号存在，推理强度写在型号名里（如 `gemini-4-neon-xhigh`）。
  - Claude Code 的推理强度用 `--effort xhigh`；Codex 用 `-c model_reasoning_effort=max`。research.py 目前不传推理强度，五步循环由主持会话自己拼命令。
- **集群要 MFA 时。** 用 `BatchMode=yes` 测试会返回 `Permission denied (keyboard-interactive)`。请用户自己在提示框运行：
  `! ssh -o ControlMaster=yes -o ControlPath=~/.ssh/cm-<别名> -o ControlPersist=8h -fN <别名>`
  之后所有 SSH 命令都加 `-o ControlPath=~/.ssh/cm-<别名> -o BatchMode=yes`。连接一旦失败就停下来报告，不尝试其他认证方式。
- **在本机跑 Codex、通过 SSH 操作集群。** 要加 `--sandbox workspace-write -c sandbox_workspace_write.network_access=true`，Codex 才能使用已建立的 ControlMaster 连接。派工前先让 Codex 运行一次 `ssh … hostname; command -v sbatch` 确认。
- **盘点时别把分段续跑误判为失败。** Slurm 显示 FAILED，可能只是外层脚本在训练未跑完时以退出码 1 结束，以便下一段续跑。先看日志里的训练返回码（如 `train_rc=0`、`done=false`、“checkpoint saved”），再下结论。
- **macOS 的 bash 3.2 和中文路径。** 变量后面直接接中文时（如 `"$WD/收到的派工单.md"`），bash 可能把中文字节也当成变量名，报 `WD�: unbound variable`。启动脚本里的变量一律写成 `${WD}`，写完用 `bash -n` 检查。zsh 里，把命令放进变量再执行（`P="python3 x.py"; $P …`）会把整串当成一个命令名，改用函数：`P() { python3 x.py "$@"; }`。
- **首稿封存。** 三方规划和三方验收都在独立的 `mktemp -d` 临时目录里运行，输出写到项目内只有主控能访问的持久目录；可用临时文件接收，再原子封存到主控目录。三份都交齐后，再复制到各角色目录并记录 SHA-256。等待期间只查看退出码和文件大小，不打开内容，也不读 Codex 的运行日志，因为日志里含草稿。
- **后台运行后要确认真的启动了。** 用后台任务派工后，过十几秒检查工作目录里是否出现日志，进度页上的状态是否已变成 running。任务失败时，先查明 Codex 是否启动、是否已提交作业，再修复并重新派发，并在事件栏记录。

## 项目归档与主控日志

同一个科研项目复用一个归档根目录。开始或恢复时先读项目说明和主控日志，定位当前轮次与最近一次交接。由主持会话在首次使用时建立以下结构，后续按轮追加：

```text
项目/
├── 项目说明.md             # 目标、完成标准、模型选择、授权范围、可选限制
├── 主控日志.md             # 全项目按时间追加的交接与决策索引
├── 进度/                  # index.html 进度页、status.json/js（scripts/progress.py 维护）
└── 轮次/
    └── 001/
        ├── 共同输入/       # 实际交给三位规划者的同一版任务与背景
        ├── Claude/         # 独立规划与独立验收的输入、答复及首稿
        ├── Gemini/         # 独立规划与独立验收的输入、答复及首稿
        ├── 主控/           # 综合方案、实际派工单、验收标准、本轮决定
        ├── Codex/规划.md    # Codex 在派工前提交的独立方案
        ├── Codex/尝试-01/  # 派工回执、脚本、结果、自检.md、执行者意见.md 和作业号
        └── 验收证据/尝试-01/  # 本次冻结的事实材料和来源索引，三方共用
```

每次尝试使用同一编号串起执行、双审和决策。例如，主控从 Codex/尝试-01/ 选取原始产物和运行记录编入验收证据/尝试-01/。执行者意见留在 Codex 目录，直到三份首稿封存才汇总。两份验收原稿分别归入 Claude/尝试-01/ 和 Gemini/尝试-01/。主控在 主控/尝试-01/决定.md 链接该版证据、三份意见，写明采纳理由和下一步，并把决定路径追加到项目日志。返工时递增尝试编号，恢复时使用日志里的轮次和尝试编号。旧项目保留原目录，日志可直接引用已有文件。

每次交接保存实际发送的任务文本和实际返回的答复；相同附件可引用本轮冻结副本。主控日志每条写明时间、轮次、阶段、发送方、接收方、输入与输出的相对路径、状态、决定和理由。Claude 的独立评审材料归 Claude 目录，Claude 作为主控作出的综合判断归主控目录。返工沿用当前轮次，给每次尝试单独编号，原始统计表、失败记录和首稿均保留。只有回到第一步重新规划时才新开一轮。

归档根目录由主控管理。独立规划与验收期间，各参与者使用独立的临时工作区，仅取得本阶段共同材料；依据前述隔离要求封存首稿，规划阶段三份、验收阶段三份交齐后再发布到本轮角色目录。主控日志在此之前只记提交状态，不透露首稿内容。大型数据、权重及受限材料保留在授权位置，索引记录服务器别名、路径、版本或校验值，以及生成它们的作业号。可共享的小型统计表与核验结果随轮次归档。

作业提交后立即登记作业号。转阶段时记录已设限额的用量和下一步。中断恢复时先核对已有产物及同一作业的状态；提交状态不明时依据唯一任务标记查调度记录，避免重复提交。连续运行依赖主持进程保持活动。相同问题反复返工仍无新证据时，记录阻碍并暂停。

### 断点续跑：关机后从同一项目接续

每次从同一项目启动，先查项目根目录的 `恢复点.md`。只有一个 Opus 主控负责更新它。首次运行即创建；每次准备派发外部动作时先落盘意图，得到回执、封存产物或决定下一步后立即更新。用同目录临时文件完整写好再原子替换，历史交接仍追加到主控日志。恢复点记录：

- 当前轮次、步骤、尝试号；目标、模型配置和剩余额度引用原记录。
- 本步各角色的动作、稳定任务标记、派工单或冻结输入版本、状态、回执位置及已完成的产物路径。独立首稿写到主控专属的持久目录，临时会话关闭后仍可取回；恢复点只存引用和封存状态。
- 已放行的检查点及适用的代码、配置版本；远程作业记录集群、提交标记、作业号、输出目录。写明重开后的第一项核对动作。

| 断开的位置 | 再次打开后的动作 |
|---|---|
| 第一步独立规划或第四步并行核验 | 检查每份完成回执与封存文件是否匹配。保留完整首稿；确认原调用已结束，才用相同输入重发缺失角色。半份输出不算交付。证据版本发生变化则另开一组核验。 |
| 第二步汇总或派工 | 若尚未形成完整派工单，从三份封存方案继续汇总。派工单已保存则核对 Codex 回执、进程和已有改动，再决定接手或补发；沿用同一任务标记。 |
| 第三步试跑或代码检查 | 对照实际代码、配置、试跑输出及 Claude 放行记录。中断的写入先查完整性；没有匹配当前版本的放行记录，就留在检查点。 |
| 第三步远程正式运行 | 提交前将唯一标记写进本地恢复点和调度作业名或注释。重连后先查同一作业号；缺号时按标记查活动队列、历史记录和远端回执。运行中继续等待，完成则核对退出状态和产物，失败则按已有训练检查点判断能否续算。无法排除已提交时暂停提交，记录待核实项。 |
| 第五步主控决策 | 已有完整决定就执行其中尚未完成的交接；决定尚未落盘，就从本轮三份封存报告继续裁决。 |

用 `checkpoint.py 项目 轮次 尝试 init` 建目录。每次派发前用 `intent --step 3 --phase pilot --role Codex --tag 稳定任务标记 --input 派工单 --input 代码或配置` 登记；三个角色并行时先登记各自的意图。输入变化或新一轮返工使用新的尝试。第三步试跑用 pilot，正式执行用 formal 和新的任务标记。主控核对试跑后，check 和 formal 都要传入同一套 --input 文件（包含实际代码、派工单与配置）以绑定放行版本。回执落盘后用 `receipt --tag 标记 --receipt 回执文件` 记录其版本。规划与核验首稿会复制到主控/尝试-NN/封存首稿；需以工具沙箱阻止参与者读取该目录。确认原调用已结束且没有回执时可用 `receipt --tag 标记 --ended`。补发前重新登记同一 intent，清除已结束状态并增加重试次数，再启动调用。恢复时读项目恢复点定位轮次和尝试，再执行 `resume` 取得该步骤每个角色的首个对账动作。主控须实际查远程记录；本工具只读本地台账，不提交作业。首稿存主控隔离目录，记录回执之前先验证完整性。

用户提前说“我要关机”时，停止派发新工作，保存恢复点，并说明哪些远程作业仍在运行。意外断电时，新主控从最后一次落盘记录与实际产物对账。若旧主持进程仍活跃，先确认交接再接管。进度页用于展示，不能仅凭“进行中”或“完成”判定是否重跑。回到项目后可输入 `/research-agent 从这个项目的恢复点继续`。

### 检查点归档
在 Skill 目录运行 `python3 scripts/checkpoint.py 项目目录 1 1 init`。两个数字分别是轮次和尝试号。将获准共享的原始产物和运行记录放入本次 Codex 尝试的“事实材料”，将后续自检与执行者意见留在上一级。
Claude 核对后，用相同的位置参数执行 `check --decision 通过 --reason "具体证据与核对结论"`。另两种决定为“返工”和“证据不足”。每次尝试只记录一次决定。
正式产物齐全后，主控逐项检查事实材料，剔除意见和受限信息，附上验收标准，再执行 `freeze`。工具复制普通文件并生成 SHA-256 清单，供三名参与者使用同一冻结副本。工具负责归档；模型调用、正式执行和材料筛选由主控负责。

## 单轮辅助脚本

需要 Python 3.8+，以及已登录且可在终端非交互运行的 claude、agy（Google Antigravity CLI）和 codex。个人 Google 账号请按 [Antigravity 官方指南](https://antigravity.google/docs/getting-started?tab=cli) 安装 agy，运行 agy 登录。命令在 PATH 中可见时，从仓库根目录运行：

```sh
python3 skills/research-agent/scripts/research.py brief.md --project /path/to/research-project --out runs/pilot-01
```

安装成 skill 后使用本文件同目录下的 scripts/research.py。默认让 Codex 只读核对项目并规划。用户要求实际执行实验时加 --execute，让 Codex 在指定工作区内写入。Gemini 评审默认使用 Gemini 4 Neon High；通过 agy models 查看可用型号，用 --gemini-model 指定其他型号。选择 default 时，Claude Code 和 Codex 分别沿用各自的模型配置。Claude 和 Gemini 在临时目录工作，主控依据任务说明与执行报告整合结论。项目数据路径提供给 Codex，任务说明及各阶段文字输出可能传给对应的模型服务。

单轮脚本每次运行使用新的输出目录。依次保存原始任务、Claude、Gemini 和 Codex 各自的规划稿、综合方案、Codex 报告与最终结论。运行中断时查看最后完成的阶段和终端错误；重新执行前核对已生成的实验文件或已提交的作业。最终汇报引用项目中的证据路径，并区分已观察的结果与待验证的假设。

## 在集群上实际执行

当用户要求跑实验、实现改动或产出结果时，选择执行模式。模型选好后，三方先独立规划，主控在本机汇总派工，执行阶段通过 SSH 把任务交给服务器上已登录的 Codex CLI。它在指定项目目录使用 workspace-write，能编写脚本、运行分析并按集群规则提交作业。远程登录环境需要能找到 codex。若授权、沙箱或调度失败，报告具体原因和已完成阶段。交付前核对真实输出；对排队作业保留 job ID 并根据用户要求追踪到完成。

```sh
python3 skills/research-agent/scripts/research.py brief.md \
  --ssh-host my-cluster --remote-project /project/my-study --execute \
  --out runs/experiment-01
```

可以复用下文的 --control-socket。三方只需一个 SSH 通道；Claude 和 Gemini 仍在本机调用。SSH 工作区由服务器端 Codex 自身的沙箱约束。

## 复核远程服务器已有结果

三个模型的 CLI 都运行在本机。已有评估终表时，先确认作业状态、回单对应的实验条件和文件更新时间，再选取这次决策需要的汇总文件。通过已配置的 SSH 别名读取指定文件，Codex 在本地 evidence 副本中复核。每个文件使用不同的文件名。示例从仓库根目录运行：

```sh
python3 skills/research-agent/scripts/research.py brief.md \
  --ssh-host my-cluster \
  --remote-file /project/eval/results/paired.csv \
  --remote-file /project/eval/results/receipt.json \
  --out runs/remote-review-01
```

SSH 默认复用别名配置的连接。已有独立 ControlMaster 时加 `--control-socket /path/to/socket`。账号需要 MFA 时，在终端完成一次该别名的认证，再复用连接。远程复核模式只读取列出的文件；文件和来源清单保存在本地运行目录。若原始材料需留在服务器，在服务器完成获准的核对，再提供可共享、可追溯的证据。说明本次直接查验了什么，以及哪些结论还需要原始材料。

用户已选择让 Antigravity 提供 Claude 时，可用 `agy models` 核对账号可选的 Claude 型号，并显式加 `--claude-agy-model claude-opus-5-5-medium`。这会将主控的输入及执行报告经 Antigravity 发送给选定型号。在五步循环中，Gemini 规划时接收共同背景，验收时另接收同一份可共享的实验产物与验收标准。
