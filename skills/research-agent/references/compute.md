# 计算资源

任务要用集群或 GPU 时读本文件：第一步规划前的资源调查、每步怎样核对资源、按节点派工、GPU 规则，以及 MFA 和 SSH 连接。硬性规则（不许退到 CPU、登录节点不计算、超额先停）的摘要在 [SKILL.md](../SKILL.md)「预算与停止」。

## 计算资源调查（计算任务必做，在第一步规划前完成）

只要任务会用到集群，主控就要在规划之前，先把计算资源查清楚，写进 `项目/计算资源.md`，并放进共同输入，让所有规划者都能看到。不能凭经验假设“可以只申请 1 张卡”或“CPU 也能跑”。调查分两部分：

1. **读官方文档。** 登录提示（`/etc/motd`）里通常有文档链接，没有就问用户。文档可以交给子 agent 读，要求它逐条附上来源链接，找不到的项写“未找到”。至少要读清：
   - 节点硬件：每节点几张 GPU、显存多大、CPU 核数和内存；
   - 分配粒度：是否整节点独占，按什么计费（节点·小时还是 GPU·小时；只用 1 张卡是否也按整节点计）；
   - GPU 的申请写法，以及在一个节点里给每个任务绑定 1 张卡的推荐写法；
   - 各分区和 QOS 的最长时限，是否有开发或测试用的快速通道（预留或测试分区）；
   - 登录节点限制；
   - 纯 CPU 任务该放在哪个分区。
2. **在集群上实查**，因为文档可能过时：
   - `sinfo -s`、`scontrol show partition <分区>`（看 OverSubscribe、MaxTime、DefaultTime）；
   - `scontrol show node <任一节点>`（看 Gres、CPUTot、RealMemory）；
   - `sacctmgr -nP show assoc user=$USER`：账号实际能用哪些分区；
   - `sacctmgr -nP show qos`：最长时限和每用户限额；
   - 预算查询命令（例如 JSC 的 `jutil user cpuquota`）；
   - 登录提示里的已知故障（例如某些 Slurm 参数被禁用）。

`计算资源.md` 写成派工可以直接引用的规则，例如：“每作业整节点 4 卡，用 `--gpus-per-task=1 --ntasks-per-node=4` 或 `srun --exclusive -n 1 --gres=gpu:1 … &` 再 `wait`”；“试跑用快速通道”；“同时最多 N 个节点（来自用户限额）”；“纯 CPU 任务打包进 GPU 作业，或提交到 CPU 分区”；“登录节点上不计算”。文档与实查结果冲突时，两者都记下，以实查为准。用户的卡数上限要换算成节点数。

## 计算资源贯穿五步

计算资源从一开始就要规划好，并在每个关键节点核查，不能浪费：

- **规划时**：每份规划都要附计算方案，按 `计算资源.md` 以节点为单位估算：几个作业，每个作业几个节点，节点里的几张卡怎样分给独立任务并行，时限多长，预计多少节点·小时和 GPU·小时。
- **派工时**：派工单要有单独的“计算资源”一节，写明分区、预留、节点数、每节点卡数、卡与任务的对应关系、时限，以及哪些任务属于纯 CPU、放在哪里跑。原则是**需要 GPU 的计算就申请 GPU**（模型前向、embedding 提取、训练、钩子审计、基于 torch 的 probe）；**只有纯 CPU 任务才不申请 GPU**（解析、统计复算、bootstrap 和置换检验、作表）。
- **派工前算预算。** Opus 按目标分区实际分配粒度核对每批作业。节点小时 = 分配节点数 × 占用小时；分配 GPU 小时 = 分配卡数 × 占用小时。派工单列出预计用量、按申请时限计算的上界、并发峰值、项目剩余额度和每张卡对应的已有任务。核对余额时计入在途作业的承诺用量，集群计费以该分区规则为准。没有用户数值限额时仍列出估算。`dispatch` 的预算参数会按这些数字拒绝超额（[workflow-commands.md](workflow-commands.md)）。
  - 例如整节点分配、每节点 4 卡，申请 1 节点 2 小时，上界是 2 节点小时、8 分配 GPU 小时。已有独立且可并行的单卡任务可同批分卡运行；只有一个短试跑时优先选合适的短时分区或缩短时限，并说明预期空闲卡数。不要为填满节点增加无关实验。
  - 如果用户限制同时占用 2 卡、分区最小分配 4 卡，不能向上取整后提交。先查是否有符合额度的分区，找不到就暂停该作业，请用户决定是否调整额度。到达上限和超出剩余预算时的做法见 SKILL.md「预算与停止」。
- **第三步试跑放行检查（主控监督）**：见下文「试跑放行的资源检查」。
- **正式运行结束后**用正式作业号核对原始结果与调度记录。第五步验收按实际分配量记录本轮用了多少节点·小时和 GPU·小时（进度工具 `job` 提供 `--node-hours` 与 `--gpu-hours`；未知留空，页面显示 —，未使用填 0），与实际时限及用户限额对比，写进决定和进度页。

## 按节点派工

先用 `scontrol show partition` 看分区是否整节点独占（`OverSubscribe=EXCLUSIVE`）。如果是，派工单按节点写，例如“每作业 1 节点 4 卡，同时最多 2 节点”，不要写“每作业 1 张卡”。一个节点上的卡要同时用满：把互相独立的试跑任务打包进同一个作业，每个任务独占 1 张卡（分别设 `CUDA_VISIBLE_DEVICES`，或用 `srun --gpus-per-task=1 --exact`），各任务单独写日志、单独记返回码。时限估紧一些，方便 backfill 调度插空。

## GPU 规则：不许退到 CPU，也不许在登录节点上计算

硬性规则（GPU 失败修好后在 GPU 上重交、不许退到 CPU、登录节点不计算、同一问题失败 3 次停下报告）在 SKILL.md「预算与停止」。派工单要把它写明。GPU 作业失败时，默认是代码或作业脚本有问题，要查明原因；模型前向、embedding 提取这类计算不能改用 CPU 跑。统计和解析可以用 CPU，但也要提交到计算节点；登录节点只用来编辑、提交和做轻量查看。检查点要核对试跑证据是否来自对应的 GPU 作业号。

曾发生过的情况：派工单写“每作业 ≤1 卡”，Codex 在环境脚本里加了检查，整节点分到 4 卡就主动退出，然后在登录节点上用 CPU 跑提取。

## 试跑放行的资源检查

主控逐项核查，任一项不合格就判返工：

1. 只核对本次试跑的作业号、运行位置、配置和实际用卡，核对分配卡数是否等于实际用卡数，用进度工具 `job` 的 `--gpus`、`--used-gpus` 分别登记分配与实测值。恢复时读取同一作业的记录，出现用卡差异由主控核对原因，按派工单说明空闲卡；正式作业号在放行并成功提交后登记。
2. 是否有卡闲置：每个任务的起止时间、绑定的是哪张卡，最好有 `nvidia-smi` 采样，也可以看 `sacct -o AllocTRES,TRESUsageInTot`。
3. 有没有退到 CPU，有没有在登录节点上计算：在登录节点上跑 `ps -u $USER`，查看 Codex 回执里列出的运行位置。
4. 时限和排队策略是否合理：试跑是否走了快速通道，时限是否估得过宽。

## 连接集群

**集群要 MFA 时。** 用 `BatchMode=yes` 测试会返回 `Permission denied (keyboard-interactive)`。请用户自己在提示框运行：

`! ssh -o ControlMaster=yes -o ControlPath=~/.ssh/cm-<别名> -o ControlPersist=8h -fN <别名>`

之后所有 SSH 命令都加 `-o ControlPath=~/.ssh/cm-<别名> -o BatchMode=yes`。连接一旦失败就停下来报告，不尝试其他认证方式。

**在本机跑 Codex、通过 SSH 操作集群。** Codex 要有网络才能使用已建立的 ControlMaster 连接：手动调用加 `--sandbox workspace-write -c sandbox_workspace_write.network_access=true`；用 workflow.py 时派工加 `dispatch --network`（只对本机 worker 生效），并加 `--scheduler-ssh <别名>`，让 `watch` 经该别名在集群上运行 `sacct`（不加时 `watch` 用 `--ssh`，两者都没有就在本机查，本机通常没有 `sacct`）。派工前先让 Codex 运行一次 `ssh … hostname; command -v sbatch` 确认。
