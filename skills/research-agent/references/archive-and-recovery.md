# 项目归档、主控日志与断点恢复

开始或恢复项目、写交接单、对账中断的调用或作业，或手动使用 checkpoint.py 时读本文件。首稿封存和证据隔离的规则在 [SKILL.md](../SKILL.md)，这里不重复。

## 归档结构

同一个科研项目复用一个归档根目录。开始或恢复时先读项目说明、`恢复点.md` 和主控日志，定位当前轮次与最近一次交接。由主持会话在首次使用时建立以下结构，后续按轮追加（workflow.py 和 checkpoint.py 会自动建出其中大部分）：

```text
项目/
├── 项目说明.md             # 目标、完成标准、档位及理由、模型选择、授权范围、可选限制
├── 主控日志.md             # 全项目按时间追加的交接与决策索引
├── 恢复点.md               # 短入口：轮次、尝试、下一步、台账和最近交接单的位置
├── 计算资源.md             # 集群文档与实查结论：节点规格、分配粒度、GPU 写法、时限、快速通道、登录节点规则
├── 进度/                   # index.html 进度页、status.json/js（scripts/progress.py 维护）
└── 轮次/
    └── 001/
        ├── 共同输入/       # 实际交给规划者的同一版任务与背景
        ├── Claude/尝试-01/  # 独立规划与独立验收的首稿（plan.md、review.md）
        ├── Gemini/尝试-01/  # 同上
        ├── Codex/尝试-01/   # 独立方案 plan.md、pilot.md、formal.md、事实材料/、自检.md、执行者意见.md 和作业号
        ├── 主控/尝试-01/    # workflow.json 台账、派工.md、放行意见.md、返工意见.md、决定.md、交接单.md、
        │                   # 封存首稿/、各阶段的输入索引与调用意图（plan/、review/、pilot/、formal/、adjudicate/、probe/）
        └── 验收证据/尝试-01/  # 本次冻结的事实材料和来源索引，审阅者共用
```

每次尝试使用同一编号串起执行、审阅和决策。例如，主控从 Codex/尝试-01/ 选取原始产物和运行记录编入验收证据/尝试-01/。执行者意见留在 Codex 目录，直到首稿全部封存才汇总。验收原稿分别归入各审阅者的 尝试-01/。主控在 主控/尝试-01/决定.md 链接该版证据和各份意见，写明采纳理由和下一步，并把决定路径追加到项目日志。返工时递增尝试编号，恢复时使用日志里的轮次和尝试编号。旧项目保留原目录，日志可直接引用已有文件。

每次交接保存实际发送的任务文本和实际返回的答复；相同附件可引用本轮冻结副本。主控日志每条写明时间、轮次、阶段、发送方、接收方、输入与输出的相对路径、状态、决定和理由。Claude 的独立评审材料归 Claude 目录，Claude 作为主控作出的综合判断归主控目录。返工沿用当前轮次，给每次尝试单独编号，原始统计表、失败记录和首稿均保留。只有回到第一步重新规划时才新开一轮。

归档根目录由主控管理。大型数据、权重及受限材料保留在授权位置，索引记录服务器别名、路径、版本或校验值，以及生成它们的作业号。可共享的小型统计表与核验结果随轮次归档。

作业提交后立即登记作业号。转阶段时记录已设限额的用量和下一步。连续运行依赖主持进程保持活动。

## 恢复点与交接单

只有一个 Opus 主控负责更新恢复点。首次运行即创建；每次准备派发外部动作时先落盘意图，得到回执、封存产物或决定下一步后立即更新。用同目录临时文件完整写好再原子替换，历史交接仍追加到主控日志。用 workflow.py 时这些都由脚本完成：调用前写 `intent-角色.json`，每次转阶段原子重写 `恢复点.md` 并追加主控日志，`handoff` 生成交接单（内容见 [workflow-commands.md](workflow-commands.md)）。

`恢复点.md` 控制在 30 行内，`交接单.md` 不超过 40 行。两者合起来要覆盖以下字段，脚本没写到的由主控在 handoff 后补到交接单末尾：

- 轮次、步骤、尝试号；目标与限制、模型配置和剩余额度（引用原记录）；
- 正在做的决定、已确认事实及证据位置、未决问题；
- 本步各角色的动作、稳定任务标记、派工单或冻结输入的版本（路径和 SHA-256）、状态、回执位置及已完成的产物路径；首稿只存引用和封存状态（存放规则见 SKILL.md）；
- 已放行的检查点及适用的代码、配置版本；远程作业记录集群、提交标记、作业号、输出目录；
- 重开后的第一项核对动作。

原始日志、完整对话、代码和报表留在归档里。新阶段用交接单及 `checkpoint.py … resume` 的输出接手，必要时按索引取证。

## 断点续跑：关机后从同一项目接续

每次从同一项目启动，先查项目根目录的 `恢复点.md`。中断恢复时先核对已有产物及同一作业的状态；提交状态不明时依据唯一任务标记查调度记录，避免重复提交。

| 断开的位置 | 再次打开后的动作 |
|---|---|
| 第一步独立规划或第四步并行核验 | 检查每份完成回执与封存文件是否匹配。保留完整首稿；确认原调用已结束，才用相同输入重发缺失角色。半份输出不算交付。证据版本发生变化则另开一组核验。 |
| 第二步汇总或派工 | 若尚未形成完整派工单，从封存方案继续汇总。派工单已保存则核对 Codex 回执、进程和已有改动，再决定接手或补发；沿用同一任务标记。 |
| 第三步试跑或代码检查 | 对照实际代码、配置、试跑输出及 Claude 放行记录。中断的写入先查完整性；没有匹配当前版本的放行记录，就留在检查点。 |
| 第三步远程正式运行 | 提交前将唯一标记写进本地恢复点和调度作业名或注释。重连后先查同一作业号；缺号时按标记查活动队列、历史记录和远端回执。运行中继续等待，完成则核对退出状态和产物，失败则按已有训练检查点判断能否续算。无法排除已提交时暂停提交，记录待核实项。 |
| 第五步主控决策 | 已有完整决定就执行其中尚未完成的交接；决定尚未落盘，就从本轮封存报告继续裁决。 |

用 workflow.py 时，无回执的调用意图用 `status` 查看，按上表核实后用 `reconcile` 对账（[workflow-commands.md](workflow-commands.md)）。

用户提前说“我要关机”时，停止派发新工作（`pause`），保存恢复点（`handoff`），并说明哪些远程作业仍在运行。意外断电时，新主控从最后一次落盘记录与实际产物对账。若旧主持进程仍活跃，先确认交接再接管。进度页用于展示，不能仅凭“进行中”或“完成”判定是否重跑。回到项目后可输入 `/research-agent 从这个项目的恢复点继续`。

## checkpoint.py

不用 workflow.py、手动编排时用它记录意图和回执。在 Skill 目录运行 `python3 scripts/checkpoint.py 项目目录 轮次 尝试号 动作`。

- **建目录。** `init` 建出各角色的本次尝试目录、Codex 的“事实材料”、`自检.md` 和 `执行者意见.md`。将获准共享的原始产物和运行记录放入事实材料，自检与执行者意见留在上一级。
- **登记意图。** 每次派发前用 `intent --step 3 --phase pilot --role Codex --tag 稳定任务标记 --input 派工单 --input 代码或配置` 登记；三个角色并行时先登记各自的意图。输入变化或新一轮返工使用新的尝试。第三步试跑用 pilot，正式执行用 formal 和新的任务标记。
- **放行。** Claude 核对后执行 `check --decision 通过 --reason "具体证据与核对结论" --input …`；另两种决定为“返工”和“证据不足”。每次尝试只记录一次决定。check 和 formal 意图都要传入同一套 `--input` 文件（包含实际代码、派工单与配置）以绑定放行版本；不一致时 formal 意图会被拒绝。
- **回执。** 回执落盘后用 `receipt --tag 标记 --receipt 回执文件` 记录其版本；第一步和第四步的首稿会复制到 主控/尝试-NN/封存首稿，需以工具沙箱阻止参与者读取该目录。确认原调用已结束且没有回执时用 `receipt --tag 标记 --ended`。补发前重新登记同一 intent，清除已结束状态并增加重试次数，再启动调用。记录回执之前先验证完整性。
- **冻结。** 正式产物齐全后，主控逐项检查事实材料，剔除意见和受限信息，附上验收标准，再执行 `freeze`。工具复制普通文件并生成 SHA-256 清单，供审阅者使用同一冻结副本。
- **恢复。** 读项目恢复点定位轮次和尝试，再执行 `resume` 取得该步骤每个角色的首个对账动作。主控须实际查远程记录；本工具只读本地台账，不提交作业。

工具负责归档；模型调用、正式执行和材料筛选由主控负责。
