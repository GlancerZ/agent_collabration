# 主控上下文、子代理与用量核算

主控上下文变大、要决定是否交给子代理、要核算 token 或耗时，或进度页的主控用量偏少时读本文件。交接的核心规则在 [SKILL.md](../SKILL.md)「主控上下文与交接」，恢复点字段在 [archive-and-recovery.md](archive-and-recovery.md)。

## 实测：主控上下文花在哪里

主控每发一次请求，都把整段上下文重发一遍（大多走缓存读取）。所以一段内容的代价约等于「它的长度 × 之后还有几次请求」，越早读进来的越贵。

**同一任务对比三种主控（2026-11-28）。** 任务：只用 Python 标准库比较二项比例三种 95% 置信区间的覆盖率；标准档一轮，三方规划和审阅用 Haiku／Sonnet，主控 Opus 5.5 xhigh，无人值守跑到第五步。

| | 改动前 | 加下一步卡片 | 卡片 + 精简工具启动 |
|---|---|---|---|
| 主控请求数 | 45 | 39 | 40 |
| 第一次请求的上下文 | 4.5 万 | 4.5 万 | 2.6 万 |
| 峰值上下文 | 18.5 万 | 12.8 万 | 10.5 万 |
| 各次请求上下文之和 | 605 万 | 340 万 | 245 万 |
| 主控费用（客户端报告） | $3.41 | $2.27 | $1.92 |
| 主控读 skill 文档和脚本源码 | 9.7 万字 | 0.2 万字 | 0.2 万字 |

三次都交付，结论和关键数字相同。每种配置只跑了一次，请求数这类小差别在波动之内；源码阅读和固定开销的差别是结构性的。

**真实项目（空间转录组，桌面版主控，2026-11-27）。** 98 次请求，第一次请求就有 7.4 万 token（几乎全是桌面版的工具定义），峰值 26.4 万并自动压缩一次，累计发送约 1,600 万 token，98% 是缓存读取。主控读脚本源码和成批读 references 约 5 万字。

由此得到的做法：

- **不读源码，按卡片走。** 改动前主控为弄懂命令，先读了 7 份 references 和几乎整份 `workflow.py`、`progress.py`，占它全部读取量的六成。现在每条命令都打印下一步卡片（[workflow-commands.md](workflow-commands.md)「下一步卡片」），`init` 一并完成进度页和用量绑定。
- **精简固定开销。** 工具定义每次请求都重发：同一句话的请求，Claude Code 默认约 3.7 万 token，按 [routing.md](routing.md) 的精简命令启动约 2 万，桌面版约 7 万。
- **剩下的多是必要开销**：读规划、回执和审阅，核对执行者的代码，以及主控自己的思考和写作（每轮输出 3 万～5 万 token；推理强度越高，留在上下文里的思考越多）。独立重算、长日志这类核对交给子代理，只取结论。
- **轮次边界清空。** `handoff` 后在终端 `/clear`，再输入 `/research-agent 从恢复点继续`；新会话先按交接单运行一次 `init` 补绑定用量。这样下一轮从固定开销重新开始，不会一路涨到触发自动压缩。

## 主控上下文

同一项决策内保持稳定的任务说明、工具和证据版本，将增量结果附在末尾。除 SKILL.md 列出的阶段边界外，转向另一项任务或发现自己在重复读取旧日志时，也先 `handoff`，再让新的主控会话接手。

**主控按决定取证。** 每次先读短交接单和本阶段的验收清单。各方看到同一份冻结索引（路径、哈希、关键值、失败及反例），可按条目读取同版原件。原件无法按需读取时把相关节选一并提供，记录未核对项。新主控只带当前决定、限制、证据索引和下一步。

**轮询交给脚本。** 轮询本身无需模型参与（分工见 SKILL.md）。回执一落盘即由主控委托的记录器登记该角色的完成时间，其余角色继续；全部回执齐后才触发汇总。

## 子代理

**Claude Code 原生子代理按需使用。** Opus 能用现有材料回答就直接决定。需要读长日志、查许多文件或核对一个独立疑点时，可发给全新上下文的只读子代理：一个明确问题、允许查看的文件及版本、判定标准。要求回传结论、关键值、证据位置及不确定项；长输出落盘。独立规划与独立验收仍用已确认的团队成员及其客户端；子代理的隔离限制见 SKILL.md。相同任务标记先查在途调用和回执。子代理也消耗上下文和时间，单次短查询直接读取即可。

**团队成员内的子代理。** 各规划者、执行者和审阅者在本角色获派阶段可按需委派；实现、运行和测试只属于第三步的执行者；优先使用该角色已选客户端、账号和型号允许的原生子代理。启动前确认当前会话有可用工具和已授权的模型路由；无法确认时由该角色自己完成。把问题、文件范围、验收条件和回传格式交给子代理，记录实际执行的子代理、用量可见范围及起止时间。由角色本人检查支持结论的证据，提交一份署名报告。各位独立评审都有权读取同一份完整证据，按需复读已有材料。待封存的意见和草稿只在本角色内可见；隔离与预算约束见 SKILL.md。

**执行者写代码时**可拆分互不重叠的文件，或将实现与独立测试分开。写入权限只授予明确的改动范围；父会话负责合并、检查差异并运行集成测试。审核阶段的子代理只读同版交付材料，回传具体发现、原件位置和未核对项。简单核对由当前会话直接完成；轮询与登记交给脚本。

## 验证速度和用量

收据记录发起、收到结果、主控交接或裁决的时间。并行阶段耗时从首次发起到最后一份回执；同时报告从末份回执到主控决定的耗时。对同一问题、证据版本、型号和强度比较完整输入与短交接，核对相同的决定、限制、反例和证据定位。列出主控与子代理的实际输入、缓存读写、输出、墙钟时间和调用数。Claude Code 有分模型用量时，对 modelUsage 各型号的输入、缓存读、缓存写和输出分别求和；这是含已归集子调用的客户端口径，不能再叠加顶层 usage。保留首次失败、重试和各自耗时。其他客户端注明子调用是否可见；缺项标未知。先核对答案，再报告实测差值；单例耗时不能外推至全项目。

按阶段登记独立请求数、输入、缓存读写和输出。有请求级数据时，平均缓存读取量用去重后的缓存读总量除以请求数；只有聚合调用记录时注明统计粒度。评估节省效果须在可比任务中同时检查核验质量和恢复点是否可用；缓存 token 数不等于订阅费用。

可在本机用以下只读命令复算所选 Claude 会话。PROJECT 取实际项目根目录；输出按会话与消息去重，列出请求数、输入、缓存读写与输出。

```sh
PYTHONDONTWRITEBYTECODE=1 PYTHONPATH="$SKILL/scripts" python3 -c 'from pathlib import Path; import sys; from progress import lead_usage; print(lead_usage([sys.argv[1]], Path(sys.argv[2]).resolve()))' "$TRANSCRIPT" "$PROJECT"
```

`lead_usage` 还接受第三个参数：额外的主控工作目录列表，含义同下文 `--lead-root`。

## 主控用量与 `--lead-root`

进度页只统计已绑定主控会话里工作目录（cwd）属于项目目录或其子目录的消息。主控若在项目的上级目录（例如仓库根目录）工作，这些消息不计入，主控用量会偏少。此时用 `workflow.py … init --lead-root 上级目录`，或 `progress.py 项目 init --lead-root 上级目录`，把该目录也算作主控工作目录；可重复，须是已存在的目录。只在已显式绑定的会话文件内生效。

## 用量来源

纯文本输出里没有用量，所以每次调用都按下表的格式发。用 json 调用时，要从 json 里取出答复正文，再存成规划稿或验收稿。workflow.py 已按此调用并登记。

| CLI | 怎样取得用量 |
|---|---|
| claude | 用 `claude -p --output-format json`，结果里有 `usage` 和 `duration_ms` |
| agy | 用 `agy -p --output-format json`。答复正文在 `response` 字段，用量在 `usage` 字段（含 `input_tokens`、`output_tokens`、`thinking_tokens`、`cache_read_tokens`、`total_tokens`），另有 `duration_seconds` |
| codex | `codex exec` 在 stderr 末尾打印 `tokens used` 和合计数，只有合计 |

**codex 客户端优先读会话文件。** workflow.py 调 codex 客户端（任何角色）时不加 `--ephemeral`，会话文件会保留，脚本从 stderr 里的 `session id:` 找到 `~/.codex/sessions/YYYY/MM/DD/rollout-*-<会话ID>.jsonl`（设了 `CODEX_HOME` 时在 `$CODEX_HOME/sessions`），用其中的 `token_count` 事件分出未缓存输入、缓存读和输出。会话文件不在本机（例如经 `--ssh` 在远程运行）时，退回 stderr 的合计数。stderr 末尾的 `tokens used` 只等于“未缓存输入 + 输出”，不含缓存读；进程被终止时也不会打印。

执行者用 codex 客户端、由当前 Codex 会话自己交付时，用 `pilot|formal --receipt 回执 --codex-session 会话ID [--since ISO时间]` 登记（执行者用其他客户端时脚本拒绝 `--codex-session`）；手动登记用 `progress.py 项目 call codex … --from-codex-session <会话ID> [--since …]`。恢复会话时加 `--since <恢复时刻>`，只计本次新增；截点含当刻，时间必须带时区。用完整会话 UUID 或明确文件，归属不明就暂停登记。

**事后补录 Gemini。** 如果已经用纯文本调用过 Gemini：agy 把每次对话都存在 `~/.gemini/antigravity-cli/brain/<对话ID>/.system_generated/logs/transcript_full.jsonl`，每一步都带 token 字段。按时间和首条请求找到对应的对话，然后运行 `call gemini 阶段 --replace N --from-agy-transcript <该目录>`，覆盖第 N 条“未记录”的调用（N 从 1 开始，按 status.json 里的顺序）。累加结果和 json 输出的数一致，已实测核对过。
